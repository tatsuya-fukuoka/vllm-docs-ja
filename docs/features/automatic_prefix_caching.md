# 自動プレフィックスキャッシュ { #automatic-prefix-caching }

## はじめに { #introduction }

自動プレフィックスキャッシュ（略して APC）は、既存のクエリの KV キャッシュを保持します。新しいクエリが既存のクエリと同じプレフィックスを共有していれば、その KV キャッシュをそのまま再利用でき、共通部分の計算を省けます。

!!! note
    vLLM が APC をどう実装しているかの技術的な詳細は[こちら](../design/prefix_caching.md)を参照してください。

## vLLM で APC を有効にする { #enabling-apc-in-vllm }

vLLM のエンジンで `enable_prefix_caching=True` を設定すると APC が有効になります。例:

[examples/features/automatic_prefix_caching/automatic_prefix_caching_offline.py](../../examples/features/automatic_prefix_caching/automatic_prefix_caching_offline.py)

## ワークロードの例 { #example-workloads }

APC が大きな性能向上をもたらすワークロードの例を 2 つ挙げます。

- 長い文書への問い合わせ。同じ長い文書（ソフトウェアのマニュアルや年次報告書など）に対して、異なる質問を繰り返す場合です。この場合、長い文書を毎回処理する代わりに、APC によって vLLM はその文書を*一度だけ*処理すればよくなり、以降のリクエストは KV キャッシュを再利用して再計算を避けられます。その結果、以降のリクエストをはるかに高いスループットと低いレイテンシで処理できます。
- マルチターンの会話。同じチャットセッション内で何度もやり取りする場合です。この場合、チャット履歴全体を毎回処理する代わりに、APC によって以降のすべてのターンで履歴の処理結果を再利用でき、はるかに高いスループットと低いレイテンシで処理できます。

## 制限 { #limits }

APC は一般に vLLM の性能を下げることはありません。ただし APC が短縮するのはクエリの処理時間（Prefill フェーズ）だけで、新しいトークンの生成時間（Decode フェーズ）は短くなりません。そのため、vLLM が回答の生成にほとんどの時間を費やす場合（回答が長い場合など）や、新しいクエリが既存のどのクエリともプレフィックスを共有しない場合（計算を再利用できない場合）は、性能の向上は得られません。
